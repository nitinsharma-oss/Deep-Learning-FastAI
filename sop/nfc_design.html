NFC Digital Identity Platform

Dashboard Design, NFC Chip Security, and Backend Approach

Technical Design Document
Version 1.0  ·  July 2026

Overview

This document consolidates the design discussion for an NFC digital identity platform — a system where a physical NFC card (a tap-enabled chip embedded in a card) resolves to a hosted digital profile. It answers three questions raised during design:

  • What should the owner and admin dashboards contain?
  • Can an NFC chip be unlocked once it has been permanently locked?
  • How should the backend be approached, given the logical flow already defined?
Core security principle

Ownership is verified server-side, not on the card. Even if someone rewrites a card's NFC memory, they cannot take over an account — the token only points to a record the server controls. This single idea shapes both the chip-locking decision and the backend design.

2.  NFC Chip Locking — Can a Locked Chip Be Unlocked?

Short answer: for the common tags, no. Once an NFC tag is permanently locked by programming its OTP (One-Time Programmable) lock bits, it becomes read-only in hardware and cannot be reverted. This is a deliberate anti-tamper feature.

2.1  Two kinds of protection

MechanismBehaviourReversible?
Password protectionTag requires a password before writing; password can be changed or removed later if knownYes
Permanent read-only lockOTP lock bits programmed once; tag becomes permanently read-onlyNo

2.2  Behaviour by chip

ChipLock behaviour
NTAG213 / 215 / 216Support permanent lock bits. Once locked, cannot be unlocked.
MIFARE UltralightSimilar — permanent lock bits are irreversible.
NTAG424 DNASecure chip with configurable features (e.g., SUN/tamper), but permanent lock bits remain permanent.

2.3  Recommendation for this platform

You don't need to lock the chip for security

The backend already guarantees that rewriting a card cannot hijack an account, because ownership is resolved server-side from the token. Locking is therefore an operational choice, not a security requirement.

Practical policy:

  • During development: leave tags unlocked so they can be reprogrammed freely.
  • Before shipping to customers, choose one of:
    • enable password protection if the token may need future updates, or
    • apply a permanent lock if the token will never change.

3.  Backend Approach

The design document defines the logical flow and the components but does not specify API endpoints or how the frontend talks to the backend. This section proposes a concrete approach built on the components already named: Resolver, Auth + OTP, Profile management, Ownership management, PostgreSQL, Redis, Object Storage, and Stripe.

3.1  System architecture

The system separates a lightweight, ultra-fast redirect path (the Resolver) from the heavier application services. Redis caches hot token→profile lookups so a tap resolves without always hitting PostgreSQL.

3.2  The tap-to-profile flow

This is the single most important path in the product and must be fast and reliable. The sequence below expands the logical flow from the design document into concrete steps.

Step by step:

  • The user taps the card; the phone opens a URL containing the token, e.g. https://tap.example.com/t/{token}
  • The Resolver receives the token and looks it up (Redis first, then PostgreSQL).
  • If the token is valid and the card is Active, it resolves to the owner's profile slug.
  • The Resolver returns an HTTP 302 redirect to /p/{slug}.
  • The profile page loads its content from the Profile Store (media from Object Storage).
  • The tap event is logged asynchronously so analytics never slow the redirect.
