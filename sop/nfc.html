System design · architecture reference

Secure NFC Digital Identity Platform

A subscription platform where each NFC card carries only an opaque token, and ownership is enforced entirely in the backend — so rewriting the chip changes nothing.

§01

The core idea

Security does not live on the NFC chip. It lives in the backend registry. The card only ever holds an opaque, non-enumerable token — never personal data. When tapped, the card opens a URL; the platform resolves that token to a cloud-hosted profile.

Because ownership is a server-side record keyed on the token, an attacker who rewrites a chip can change what one physical card points to, but cannot move ownership or hijack anyone's profile. The rewrite is inert. Locking the tag to read-only (where the chip supports permanent lock bits) closes even that gap. The real, defensible guarantee is not "the chip can't be rewritten" — it's "rewriting the chip does nothing the platform respects."

§02

System architecture

The system is a three-layer stack. Everything except one box is standard web infrastructure; the highlighted ownership registry is the part a generic NFC card doesn't have.

Client layer

The visitor needs no app — tapping opens a URL in whatever browser the phone already has, which is why the card stores only a token. The owner and admin reach a real authenticated dashboard.

Application layer

Two paths that scale independently. The resolver is the read-only hot path on every tap: fast, cacheable, stateless. Auth, profile editing, and ownership control are lower-traffic, higher-security write paths. A viral card getting 50,000 taps never slows editing and never touches the ownership-write machinery.

Data layer

Where the product lives. The ownership registry holds the authoritative token → account binding — the single source of truth that makes rewriting a chip pointless. Large assets (resumes, portfolio images) sit in object storage, not the database. The cache/analytics store absorbs the tap-event firehose asynchronously so logging never blocks a redirect.

§03

Card ownership lifecycle

This state machine is the security model. Ownership only ever changes through admin approval, and an unauthorized rewrite produces no transition at all.

Two properties define the whole guarantee. First, the only edge into "bound to a new owner" runs through admin approval — verification plus an audit trail. Second, an unauthorized rewrite has no transition at all: bytes on a card changed, but since the registry never consulted those bytes, nothing happened server-side.

§05

Key design decisions

Token: long, random, non-enumerable

cards.token is the most-hit index in the system — every tap looks it up. Make it 128-bit, base62-encoded (~22 chars), unique and indexed. No one should guess a neighbor's token by incrementing.

Deliberate denormalization on the hot path

cards carries both owner_id and profile_id even though the owner is derivable through profiles. That lets the resolver answer "who owns this, what do I serve" from a single indexed row read — no joins. The invariant card.owner_id == card.profile.account_id is enforced by the write path, not trusted from callers.

Ownership transfers are append-only

Never update or delete a row — only insert. This table is both the audit log and the legal record of who owned a card when. Activation is the first transfer (from_account null); real transfers and lost-card reissues are later rows. Because nothing mutates it, it can't be quietly rewritten.

Redirect, don't render, at the token URL

The tap path returns a 302 to a stable profile URL (profiles.slug) rather than rendering at the token URL. Token and profile stay decoupled: a lost-card reissue points a new token at the same profile, and the owner's shared link (QR, email signature) never breaks. The token is disposable; the profile identity is permanent.

Status enums + soft delete

Explicit enums (provisioned / active / revoked for cards; active / suspended / deleted for profiles) and soft delete via status rather than hard DELETE, so a revoked card's history survives.

Suggested stack

Next.js for server-rendered public profiles and the dashboard; a Go or Node resolver for the hot path; Postgres for the registry and accounts; Redis for token-resolution caching; S3-compatible object storage for assets; Stripe for subscriptions via webhooks. None of it is load-bearing — just the least surprising choices for this shape of system.
